# BFS 與 Dijkstra 加權網格視覺化



## 專案簡介



這個專案將我先前使用 C++ 練習的 BFS 與 Dijkstra，重新翻譯成 JavaScript，並透過網頁動畫呈現兩種演算法搜尋加權網格的過程。



我製作這個視覺化工具，是因為只看程式碼時，不容易直接觀察 BFS 與 Dijkstra 選擇路徑的差異。透過同一張地圖，可以看出 BFS 尋找最少步數，而 Dijkstra 尋找最小權重總和。



## 主要功能



- 顯示 10×10 加權網格

- 每個可通行格子的權重為 1～9

- 使用 `-1` 表示牆壁

- 左上角為起點 S，右下角為終點 T

- 以淺藍色動畫顯示演算法的拜訪順序

- 以橘色顯示最後選擇的路徑

- BFS 顯示最短步數

- Dijkstra 顯示最小總成本

- 提供重設功能



## 操作方式



本專案不需要安裝框架或套件。



1. 下載或 clone 這個 repository。

2. 開啟 `visualizer/index.html`。

3. 按下「執行 BFS」或「執行 Dijkstra」。

4. 觀察搜尋順序、最後路徑與結果。

5. 按下「重設」可以重新播放。



也可以在 Windows CMD 的 repository 根目錄執行：



`start visualizer\index.html`



## BFS 與 Dijkstra 的差異



| 比較項目 | BFS | Dijkstra |

|---|---|---|

| 選擇下一個狀態 | 依照先進先出的順序 | 選擇目前累積成本最小的狀態 |

| 是否考慮權重 | 否 | 是 |

| 找到的目標 | 最少步數 | 最小權重總和 |

| 適用情況 | 無權圖或每條邊成本相同 | 邊權重皆為非負數的加權圖 |

| 本專案顯示結果 | 步數 | 總成本 |



目前地圖中，BFS 選擇 18 步、權重總和為 70 的短路；Dijkstra 選擇 22 步、總成本為 22 的長路。



## 地圖設計



這張測試地圖是我自己設計的，目的是讓 BFS 與 Dijkstra 在同一張地圖上選出不同路徑。



設計時必須同時滿足兩個條件：



1. 短路只有 18 步，但途中包含高權重格子，因此總成本為 70。

2. 長路需要 22 步，但經過的格子權重都是 1，因此總成本為 22。



所以 BFS 會選擇步數較少的短路，而 Dijkstra 會選擇總成本較低的長路。這張地圖能直接呈現「最少步數」和「最小總成本」並不一定相同。



## 程式架構



程式分成「演算法」與「播放器」兩部分。



演算法函式：



- `runBFS(grid, start, target)`

- `runDijkstra(grid, start, target)`



兩個函式都回傳：



`{ visitOrder, path, cost }`



其中：



- `visitOrder`：演算法處理格子的順序

- `path`：從起點到終點的最後路徑

- `cost`：BFS 的步數或 Dijkstra 的總成本



播放器只負責畫出網格與播放動畫，不參與演算法計算。這讓演算法邏輯可以和畫面功能分開測試與修改。



## 實作方式



### BFS



BFS 使用陣列模擬 queue：



- `push()` 從尾端加入

- `shift()` 從前端取出

- 使用 `dist` 判斷格子是否已經拜訪

- 使用 `parent` 還原最短步數路徑



### Dijkstra



JavaScript 沒有直接對應 C++ `priority_queue` 的內建資料結構，因此這個 10×10 demo 使用候選陣列，每一輪掃描並找出距離最小的狀態。



找到更小的距離時，程式會更新 `dist`、記錄 `parent`，並將新狀態加入候選陣列。取出狀態時也會跳過已經過期的距離資料。



## 複雜度



令格子數量為 `V = H × W`。



- BFS 演算法概念上的時間複雜度為 `O(V + E)`。

- 目前 JavaScript 使用 `shift()`，適合這個小型展示；若地圖變大，可以改用 head 索引避免移動陣列元素。

- 目前的 Dijkstra 每輪使用線性掃描尋找最小狀態，時間複雜度約為 `O(V²)`。

- 若要處理大型地圖，應改用 binary heap，將效率改善為接近 `O((V + E) log V)`。

- `dist`、`parent` 與動畫資料所需空間約為 `O(V)`。



## 學習收穫



這次實作讓我發現，同樣是尋找路徑，BFS 與 Dijkstra 判斷「最好路徑」的方式並不相同。



BFS 只在意到達終點需要幾步，即使途中經過高權重格子也不會受到影響。Dijkstra 則會比較累積成本，因此可能選擇步數較多、但總成本較低的繞路。



我也學到，演算法不一定要直接控制畫面。只要回傳拜訪順序、路徑與成本，就能由另一部分程式負責播放動畫。這讓程式的責任更清楚，也比較容易除錯。



## AI 使用說明



本專案的 HTML、CSS、Canvas 畫面與動畫播放器骨架由 AI 產生。



`runBFS` 與 `runDijkstra` 兩支演算法，是我根據自己先前完成的 C++ 程式，自行翻譯成 JavaScript。



用來比較 BFS 與 Dijkstra 的加權地圖也是由我自己設計，目標是讓短路有 18 步但成本較高，長路有 22 步但每格權重都是 1。



AI 在過程中協助檢查程式、提供逐步提示與 README 結構建議，但沒有直接提供這兩個演算法函式的完整實作。
